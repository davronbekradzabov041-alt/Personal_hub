# Формат внешнего модуля (Этап 11)

Внешний модуль — декларативный пакет данных и ресурсов. **Никакого
исполняемого Dart/любого другого кода в нём быть не может.** Ядро
никогда не выполняет код из внешнего пакета — оно только читает
`manifest.json` и (позже, не на этом этапе) ресурсы из `assets/`/`data/`.

## Структура

```
module/
 ├── manifest.json   — обязателен, единственный источник метаданных
 ├── assets/         — статические ресурсы (иконки, изображения и т.п.)
 ├── data/            — данные модуля (например, начальные записи)
 └── README.md        — произвольное описание для человека, необязателен
```

`assets/` и `data/` могут быть пустыми.

**Уточнение (Module Platform).** На Этапе 11 содержимое этих
директорий не регламентировалось. Сейчас формат внутри них
зафиксирован в коде и проверяется при каждом импорте
(`PackageSecurityGuard.validateArchive`):

- `assets/` — плоско, без поддиректорий, только расширения
  `.png`, `.jpg`, `.jpeg`, `.webp`, `.svg`, `.json`;
- `data/` — только файл `data/storage.json`, больше ничего;
- другие директории верхнего уровня, кроме `assets/` и `data/`,
  отклоняются;
- размер каждого файла и всего архива ограничен.

То есть это по-прежному «ресурсы и данные, а не код», но набор
допустимого внутри теперь определён и описан в коде, а не только в
этом документе.

## manifest.json — обязательные поля

| Поле | Тип | Описание |
|---|---|---|
| `id` | string | Уникальный идентификатор модуля, непустой |
| `name` | string | Отображаемое имя |
| `version` | string | Версия модуля, строгий формат `X.Y.Z` (major.minor.patch), например `1.0.0` |
| `apiVersion` | int | Версия Module API ядра, под которую собран модуль |
| `author` | string | Автор/издатель |
| `description` | string | Короткое описание |
| `permissions` | string[] | Запрашиваемые разрешения (см. `ModulePermission`) |
| `dependencies` | object[] | Зависимости от других модулей: `{"id": "...", "minVersion": "..."}` |
| `icon` | string | Путь к иконке внутри `assets/` или её идентификатор |

Все девять полей обязательны для ВНЕШНЕГО пакета — в отличие от
собственных (встроенных) модулей ядра, где `description`/`icon`/
`permissions`/`dependencies` необязательны и по умолчанию пусты
(см. `ModuleManifest`, Этап 7). Для недоверенного внешнего пакета
умолчания маскировали бы то, что автор просто забыл указать поле —
поэтому `ManifestParser` требует их присутствия явно.

## Что проверяется и где

| Проверка | Где реализована |
|---|---|
| Повреждённый JSON | `ManifestParser.parse` |
| Отсутствующие поля | `ManifestParser.parse` |
| Пустой `id` | `ManifestParser.parse` (через `ModuleManifest.fromJson`) и повторно `ManifestValidator.validate` (defense-in-depth) |
| `apiVersion` не число | `ManifestParser.parse` (через `ModuleManifest.fromJson`) |
| Неверный формат `version` (не `X.Y.Z`) | `ManifestValidator.validate` и повторно `ModuleManager` перед `tryInstall()` (defense-in-depth) |
| Неподдерживаемая версия Module API (число вне диапазона) | `ManifestValidator.validate` |
| Дублирующийся `moduleId` | `ManifestValidator.validate` (принимает `existingModuleIds` извне) |
| Циклические зависимости | `ManifestValidator.findDependencyCycles` — принимает граф `Map<String, List<String>>`, архитектура готова, реального многомодульного графа в приложении пока нет |

## Что НЕ входит в Этап 11

Импорт ZIP-архивов, выбор файла пользователем, чтение с диска, сеть,
скачивание, установка модуля в `ModuleRegistry`/`ModuleManager`,
выполнение любого кода из пакета, Module Store UI. Этот этап создаёт
только формат (структуру + `manifest.json`) и его валидацию
(`ManifestParser`, `ManifestValidator`, `ModulePackage`,
`ModuleImportResult`) — из голой строки JSON и явно переданных списков
путей, без единого обращения к файловой системе.
